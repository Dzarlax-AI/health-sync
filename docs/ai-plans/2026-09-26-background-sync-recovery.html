Восстановление фоновой синхронизации

26 сентября 2026 · health-sync · codex/background-sync-recovery · исходная ревизия 5f89724 · реализация согласована

1. Вывод и цель

В коде найдены причины, по которым приложение может перестать отправлять данные в фоне и восстановиться после открытия. Пользователь подтвердил: после открытия отправка работает, приложение свайпом не закрывается. Приоритет — восстановить существующий механизм HealthKit + BackgroundTasks и сделать его состояние проверяемым.

Это анализ исходников, истории Git и документации Apple. Логи с телефона, версия установленной сборки и фактические атрибуты её Keychain пока не проверены. Найденные дефекты подтверждены кодом; конкретная цепочка сбоя на устройстве остаётся гипотезой. На момент исходного анализа код ещё не менялся. Реализация и результаты последующих проверок приведены в разделе 10.

2. Что происходит сейчас

AppDelegate синхронно регистрирует observers на шаги, пульс, активную энергию и сон. Каждый callback вызывает общий SyncEngine. Есть два BGProcessingTask: обычная синхронизация и пересканирование семи дней после 03:00. Entitlements HealthKit/background-delivery и разрешённые task identifiers присутствуют.

Движок перечитывает диапазоны дат, сохраняет границы незавершённой работы и принимает успешность только после проверки ответа сервера. Транспорт использует обычную URLSession с timeout 120 секунд. Отдельной очереди сериализованных payload и системной background URLSession нет. Время жизни загрузки зависит от доступного приложению фонового времени.

3. Предлагаемый первый этап

  1. Исправить хранение и чтение credentials. Выделить Keychain-адаптер, различать отсутствующий ключ, временно недоступный ключ и прочие OSStatus. Для новых записей использовать AfterFirstUnlockThisDeviceOnly. При разблокированном приложении обновить accessibility существующей записи без удаления и без изменения значения. Проверять результат миграции; не считать её успешной при ошибке.
  2. Отделить настройки планирования от секретов. Для синхронной регистрации observers достаточно настройки backgroundSync и несекретных параметров. Ошибка чтения credentials должна откладывать работу, сохранять pending/checkpoints и диагностироваться, а не выключать background delivery. Полную конфигурацию проверять перед отправкой. Явное выключение пользователем продолжает отменять фоновые задания и subscriptions.
  3. Сделать планирование идемпотентным. Через адаптер BGTaskScheduler проверить pending requests, сохранять уже назначенную более раннюю заявку, включая просроченные 03:00. Новую создавать при отсутствии заявки, после фактического запуска либо при осмысленном изменении настройки. Сериализовать операции, чтобы callback проверки не воскресил задания после выключения. Обрабатывать ошибки submit/register.
  4. Восстанавливать фоновый цикл. При доступности protected data и при активации повторять отложенную настройку/миграцию и допустимую незавершённую работу. Состояние регистрации observers отделить от успешности enable delivery по каждому типу. Повторять только неуспешные enable на подходящем lifecycle-событии, без непрерывного retry loop. Сериализовать off→on, чтобы поздний callback disable не выключил новое включение.
  5. Закрепить завершение фоновых обработчиков. Единый однократный completion для success/error/expiration; отмена только владельцем соответствующей работы. Сохранить незавершённые диапазоны, не продвигать checkpoints на locked/cancelled/неподтверждённом upload. Не возвращать ранний completion до сохранения необходимого состояния.
  6. Добавить компактную диагностику в Settings. Последний фоновый триггер, причина и итог попытки, подтверждённая отправка, состояние scheduler/delivery, временная недоступность данных или credentials, системный background refresh и Low Power Mode. Хранить ограниченный локальный набор событий без API key, payload, значений метрик и URL. Новые UI-строки — en/ru/sr, цвета — через Color.ds*.

Критерий результата: временная блокировка не отключает механизм; заявка не отодвигается при каждом refresh; успешная фоновая доставка подтверждается сервером на реальном устройстве. Фиксированное расписание каждые 15 минут не обещается.

4. Виджет и границы изменений

Виджет полезен как второй этап: «последняя подтверждённая отправка», «данные ожидают отправки», переход в приложение для синхронизации. WidgetKit имеет отдельный бюджет обновлений и не держит основное приложение запущенным. Он не устраняет ошибку credentials и ограничения доступа к HealthKit.

Первый этап не добавляет Widget Extension, App Group, push-инфраструктуру, HealthKit anchors или background URLSession. Надёжная передача уже собранного payload через системную URLSession потребует отдельного проекта: защищённые файлы очереди, account isolation, обработка relaunch и ACK, очистка и дедупликация. Возвращаться к этому стоит, если диагностика после исправлений подтвердит срыв сетевой передачи при suspension.

Серверный API, формат payload, правила sleep coverage и обработка на сервере сохраняются. Меняются клиентское хранение credentials, фоновой lifecycle и небольшой блок диагностики.

6. Проверки

Сначала тесты, воспроизводящие ошибочные решения на injected Keychain/scheduler/clock/HealthKit dependencies; реальные credentials и сервер в автоматических тестах не использовать. До запуска проверить test mode и отключение уведомлений для тестовой сборки.

  • Locked Keychain на cold launch: observers регистрируются; задания/delivery не отменяются; запрос без ключа не отправляется.
  • Миграция сохраняет значение и account fingerprint; error/notFound/locked различаются; неуспешная миграция повторяется после unlock, не уничтожая запись.
  • Повторные refresh не отодвигают ранний запрос; просроченные 03:00 сохраняются; после выполнения назначается следующий день. Проверить смену часового пояса/DST и изменение интервала.
  • Неуспешное enable delivery повторяется без дублирования queries; быстрые off→on и поздние callback не приводят к неверному конечному состоянию.
  • Success/error/expiration/cancellation дают ровно один observer completion и BGTask completion; expiration одного waiter не отменяет работу другого владельца.
  • Locked HealthKit, медленная сеть и expiration не продвигают checkpoints. Account switch, частичный ACK, retry и sleep coverage проходят существующие регрессионные тесты.
  • Диагностика не содержит секретов/health payload; видна в light/dark и крупном Dynamic Type.

7. Риски, допущения и откат

  • AfterFirstUnlockThisDeviceOnly делает ключ доступным приложению после первой разблокировки до перезагрузки, включая последующие блокировки. Он не переносится на другой телефон при восстановлении backup; там потребуется повторный ввод. Это осознанное изменение защиты credentials.
  • Сам HealthKit может оставаться недоступным при блокировке. Исправление Keychain не открывает HealthKit и не гарантирует wakeup при каждом unlock. Lifecycle notification помогает уже работающему процессу; последующие HealthKit/BGTask запуски также должны восстанавливать работу.
  • Изменять account guard так, чтобы старые credentials могли отправлять после смены аккаунта, нельзя. Временная недоступность должна вести к defer, а не к обходу проверки.
  • Обычная URLSession не гарантирует завершение после suspension. Первый этап делает это наблюдаемым и сохраняет диапазоны для повтора, но не обещает системную очередь upload.
  • Фактические атрибуты Keychain, OSStatus, background refresh, энергосбережение и установленная версия неизвестны. Сбор логов должен разрешить эти неизвестные без вывода ключа.
  • Откат: отменить только изменения этого этапа. Не удалять sync-state, историю и ключ. Миграцию accessibility откатывать отдельным проверяемым SecItemUpdate на разблокированном устройстве, только при явном решении вернуть прежнюю защиту.

10. Реализация и проверка

Реализовано локально; device QA остаётся невыполненной. Ниже результаты фактических проверок, отдельно от исходных гипотез.

  • KeychainStore.swift: проверяемый адаптер Security, отдельные notFound/locked/OSStatus error, запись с AfterFirstUnlockThisDeviceOnly, идемпотентная миграция существующего item без удаления.
  • SyncConfiguration.swift: несекретный BackgroundSettings; AppDelegate синхронно регистрирует observers независимо от ключа. Миграция и повтор неуспешной настройки — при запуске/активации/unlock.
  • BackgroundScheduling.swift: сериализация scheduler/delivery, сохранение ранних и просроченных заявок, изменение интервала меняет только обычное задание. Ошибки отражаются в диагностике.
  • BackgroundSyncManager.swift: раздельный учёт queries и delivery по типам, последовательный off/on, однократное завершение callback при expiration. Отложенная работа повторяется после доступности protected data, включая частичную отправку с заблокированным вторым каналом.
  • SyncEngine.swift: временная недоступность credentials не теряет durable state и не разрешает отправку с закэшированным ключом. Сохранены проверки конфигурации после async-операций и изоляция владельцев отмены.
  • BackgroundSyncDiagnostics.swift, Settings и SyncStatus: локальный журнал максимум 40 событий с закрытым словарём, время последнего фонового приёма, системные ограничения. 29 новых строк en/ru/sr; все ранее существовавшие переводы сохранены без изменений.

11. Установка на iPhone

По явной команде пользователя «ставь на iphone» собрана Release-конфигурация из текущей ветки и установлена на подключённый физический iPhone 16 Pro Max поверх приложения с bundle ID com.dzarlax.health-sync. xcodebuild завершился BUILD SUCCEEDED; devicectl device install app подтвердил установку. Подпись проверена; entitlements HealthKit и background-delivery включены.

Приложение успешно запущено на iPhone. После явного разрешения обычной синхронизации и подтверждения прежнего сервера проверен сохранённый URL в настройках этого устройства. Затем devicectl device process launch подтвердил запуск; отдельная проверка processes нашла работающий процесс Health Sync (PID 1771). Предыдущие попытки были заблокированы проверкой разрешений до запуска, а не завершились сбоем приложения. Применение миграции на телефоне, серверный приём и естественная фоновая отправка отдельно пока не подтверждены.

Локальные доказательства: /tmp/health-sync-background-device-build.log , /tmp/health-sync-device-install.json и /tmp/health-sync-device-launch.json. Данные приложения не удалялись; uninstall не выполнялся.
