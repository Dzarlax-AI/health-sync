3. Желаемый пользовательский путь

  1. Today: существующая готовность и энергия; ниже явно разделённые «Инсайт сервера» и «AI-инсайт». При preview видна пометка. Короткие карточки сна, восстановления и энергии ведут в детали. «Изменения за день» появляется только при непустом серверном списке.
  2. Сон: добавить пару инсайтов текущего дня к существующим данным/графикам. Не выдавать текущий инсайт за исторический вывод при выборе прошлой ночи. Существующие графики продолжают работать при сбое optional API.
  3. Восстановление: аналогичная пара в существующем SectionDetailView для recovery; сохранить серверные KPI, графики и объяснения.
  4. Энергия: отдельный экран внутри NavigationStack, без шестой вкладки. Текущий запас/ёмкость и доступные детали из briefing, серверный и AI-инсайт, 14-дневная история из /api/energy-history?granularity=day&days=14. Исторический current_eod подписать как дневное значение, не почасовую текущую энергию; отрицательные значения не обрезать до нуля. Пустая/ошибочная история не блокирует инсайты и текущую энергию.
  5. Совместимость: отсутствие AI, старый сервер, генерация, ошибка или недостаток данных сохраняют полезный серверный контекст. При наличии нового Today snapshot не показывать дублирующий legacy AI-текст.

UI chrome переводится через xcstrings (EN/RU/SR), серверный контент остаётся в report_lang. Цвета только через DesignSystem. Никаких новых уведомлений или фоновых запросов для dashboard.

4. Контракт и обновление

  • Добавить optional AI Insight на верхнем уровне и у доменов: text, stance, alternative_action, fact_ids, evidence_ids. Сохранить ссылки, но не показывать пользователю внутренние ID. Новые string enum значения не ломают decode.
  • Добавить optional narrative_mode и slots с key/state/fresh_for_snapshot/retry_after_seconds. Отсутствие additive полей допустимо. Не считать глобальную свежесть доказательством свежести каждого AI-слота; устаревший AI не показывать как текущий.
  • TodayInsightsController: тестируемые loader/clock, отмена и защита от поздних ответов. Только активный видимый экран опрашивает API. Disabled перепроверяется раз в 60 секунд без расходования бюджета генерации. Cold/generating/failed — ограниченные повторы (10), уважение серверного retry_after без преждевременного сокращения backoff. При возвращении на экран/смене дня/ручном обновлении контекст проверяется заново.
  • Смена URL, ключа/аккаунта, report_lang или дня не должна наследовать предыдущий snapshot. На transient network error можно сохранить только явно устаревший контекст того же аккаунта/дня. 401 не маскировать успешным состоянием.
  • Загрузка Today snapshot, основной информации и Energy history независима; долгий или неуспешный вспомогательный запрос не задерживает готовую карточку. Legacy fallback использует существующие данные при отсутствии нового контракта.

7. Риски, допущения и откат

  • Смёрженный PR может ещё не быть выложен; приложение должно быть совместимо с обеими версиями. Старые записи памяти о B1 disabled не являются проверкой текущих tenant-флагов.
  • Новый AI остаётся экспериментальным: UI показывает серверную пометку preview и не объявляет прохождение product gate. Включение AI и платные provider-вызовы управляются сервером.
  • Опрашивание API само может запускать серверную генерацию при включённом режиме. Использовать согласованный контракт, не добавлять собственную кнопку генерации или вызовы AI-провайдера.
  • Дневная история EnergyBank совместима с новым web-экраном; отдельный почасовой v2-график не входит в этот перенос. Формулы не дублируются на клиенте.
  • По умолчанию новый экран открывается из Today. Отдельная вкладка энергии не требуется для parity.
  • Откат — выборочно отменить только изменения инсайтов/энергии, сохранив текущую работу по синхронизации. Миграций, смены ключей и серверных изменений нет.

Неблокирующие неизвестные: фактическая production-версия и tenant-preview; они проверяются перед device QA. Архитектурных вопросов, требующих дополнительных вариантов от пользователя, после анализа не осталось.

Счётчики и бизнес-смысл берутся из существующих API; backend и синхронизация не меняются. Сохраняются независимые ошибки и отсутствие данных. Production-deploy и commit/push не входят в эту правку.

Риски: контраст, длинные строки, переполнение и отсутствие некоторых данных. Откат — только изменённое представление по сохранённым копиям; прежние исправления данных/синхронизации сохранить. Разрешение на реализацию получено текущим сообщением; повторный approval не требуется.
